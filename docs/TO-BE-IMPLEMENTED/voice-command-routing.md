# 语音指令选引擎（名词用手选，动词用嘴说）

> **状态**：待调研（方向已讨论，未开始实现）
> **提议日期**：2026-10-18
> **优先级**：中（产品方向级设想，非阻塞）
> **预估工作量**：v0 约 300–500 LOC（纯本地）；v1 另需一个小转发后端 + Jev 接入
> **前置**：先完成第 6 节「待调研清单」，再决定做不做、做到哪一步

---

## 1. 背景与动机

触触搜想做到「让用户随心所欲地搜：想搜什么、到哪里搜」。现状的天花板：

- 引擎是我们一个个写进 `config/unifiedMenuConfig.json` 的，加一个就要发一版；
- 引擎越多，右键菜单 / Popup / 侧边栏的列表越长越难找——**「引擎多」和「好用」互相打架**；
- 侧边栏已有语音选引擎（见 `docs/archive/voice-engine-picker.md`），但只能说引擎名、靠别名表模糊匹配，
  口语化说法（「去种草社区看看」「让双子座答一下」「百度，不对，谷歌」）基本认不出。

---

## 2. 用户原始诉求（口述实录，2026-10-18）

1. 「我这个产品就是想实现那种比较强大的功能：让用户随心所欲地去搜索想搜的引擎。现在局限于目前只有这么几个引擎。」
2. 「有没有一个比较具有突破性或创新性的方案，既能方便用户实现『想搜什么、到哪里搜』，用起来又特别方便？」
3. 「用语音，然后再结合一些云端的 API，比如说 JEV」——指 TypeSafe 的 Jev（见第 4.3 节）
4. 「我们想实现类似 Typeless 那种模式……语音转换成精确指令……关键字参数则根据用户选中的即可。这样就很好的限定用户只需要发出精确的指令动作来选定某个引擎……然后用户得到『想要的搜索动作』。」

关键词：语音 → 精确指令 / 关键词 = 选中文字 / 只用嘴选引擎和动作 / Typeless 式手感

---

## 3. 核心设计

### 3.1 分工：名词用手选，动词用嘴说

| | 来源 | 为什么 |
|---|---|---|
| **关键词（名词）** | 用户选中的文字 | 不经过语音识别，一个字都不会错 |
| **去哪 / 做什么（动词）** | 用户说的一句短口令 | 选项是有限集合（现有菜单项），是一道选择题，识别容易做准 |

不需要大模型「理解整句话」，也不需要从语音里抽关键词——Jev 不能生成文字的短板正好绕开。

### 3.2 交互：按住说，松手搜（Typeless 式）

```
1. 选中「XX 相机」
2. 按住快捷键（或按一下开始），选区旁浮出小窗：
     🎙 正在听…  ▁▃▅▇▅▃▁
3. 说「小红书」/「去红书看看」/「让双子座答一下」/「嗯…百度，不对，谷歌」
4. 松手（或说完停顿）：
     → 小红书 · 搜「XX 相机」   ✓
   新标签打开
```

- **置信度高** → 直接执行（开标签是可撤回的低风险动作），浮窗显示去了哪里；
- **置信度低** → 浮窗给概率最高的 3 个候选（如「小红书 / 知乎 / 速答·Claude」），点一下执行；
- 口语里的自我更正（「百度，不对，谷歌」）以最后一次为准——这是 Typeless 的精髓；
- 坚持现有原则：只打开 / 填入，**不自动发送、不自动发布**。

### 3.3 Typeless 参考点（待调研细化）

Typeless 是一款 AI 语音输入工具：按住快捷键说话、松手就把口语（含停顿词、自我更正）整理成干净结果放到光标处。
我们借鉴的是手感——**按住即录、松手即出结果、自动清理口语噪声**——但输出不是一段文字，而是一个确定的菜单动作。

## 4. 技术方案（草案）

### 4.1 数据流

```
网页里按快捷键（content script 记下选中文字）
  → SW 拉起 offscreen/voice.html 录音 + 识别（复用现有 ccsVoiceRecognize）
  → 得到一句口令文字
  → 判断去哪：Jev（v1）或本地别名匹配（v0 / 兜底）
  → executeMenuAction({ menuItemId, keyword: 选中文字 })（复用现有菜单动作）
  → 浮窗显示结果 / 低置信度时显示 3 个候选
```

### 4.2 可直接复用的现有代码

| 现有能力 | 位置 | 用途 |
|---|---|---|
| offscreen 录音 + Chrome 自带语音识别（含麦克风授权页） | `offscreen/voice.js`、`voice-permission/`、`src/background/voiceOffscreenBridge.ts`（`ccsVoiceRecognize`） | 不用每个网站单独弹麦克风权限 |
| 引擎别名表（「度娘」「鸡屁屁」「杰米尼」…）+ Levenshtein 匹配 + 历史 reranker | `sidepanel/voice.js` 的 `VOICE_ALIAS_MAP` / `aliasMatchScores` | v0 的匹配器；v1 里当作 Jev 选项的说明文字；Jev 不可用时兜底 |
| 菜单结构（右键 / Popup / 侧边栏同源） | `getMenuStructure` → `src/background/popupMenuStructure.ts` | **指令清单从这里自动生成**，加引擎后语音自动能说它 |
| 执行菜单动作 | `executeMenuAction`（`background/events/menu.js`） | 关键词 = 选中文字，直接复用 |

粗算现有可执行菜单项约一百个（`unifiedMenuConfig` 37 项 + 速答 / 百问各 6 引擎 + 优化 8 类 × 引擎 + 封面 7 风格），
低于 Jev 单个 Choice 的 255 上限，可以摊平成一道选择题；以后引擎上千时按 Jev 文档的两步法（先选大类，再选站）。

### 4.3 Jev（TypeSafe）——据 2026-09/10 官方博客与文档，**未经我们实测**

- 来源：<https://typesafe.ai/blog/introducing-system-one-models-and-jev>、<https://docs.typesafe.ai/introduction>、
  <https://docs.typesafe.ai/introduction/quickstart>、<https://docs.typesafe.ai/primitives/choice>
- 定位：「System One」模型——不生成文字，给一段「状态」（文字 / JSON）和若干预定义类型的问题，返回结构化判断。
- 问题类型：**Choice**（最多 255 个选项，返回 `choice` + 全部选项的 `probabilities` + `confidence`）、
  **Score**（按标准打分）、**Noul**（一句话为真的概率 0–1）；多个问题可放一次请求并行回答。
- 接口：`POST https://api.typesafe.ai/v1/systemone`，`Authorization: Bearer <API_KEY>`，模型 `jev-latest`；
  有 Python / Node SDK，文档未说明浏览器端用法。
- 官方声称：端到端 70–500 ms；输入 $0.042 / 百万 token，输出免费（官方自承「还证明不了价格没有补贴」）。
- 现状：**抢先体验，需排队申请**。
- 没有内置「以上都不是」，文档建议自己加一个 `other` 选项；没有多选。

v1 的一次请求大致是（示意，非确切格式）：

```
状态：口令 = "去红书看看"；（可选）选中文字摘要；当前网站 = x.com
问题：
  去哪 / 做什么（Choice）：每个菜单项一个选项，说明 = 引擎名 + 别名，外加 other
  是否说清楚了（Noul）：用户是否明确说了去哪
```

### 4.4 隐私

- **默认只发那句很短的口令**，选中文字不发；只有用户只说了「搜一下」、没说去哪时，才带上选中内容让它按内容推荐（可设开关）。
- 录音只在按住快捷键 / 主动触发时进行，**不做一直在听的唤醒词**。
- 商店描述「全部本地处理」与隐私政策需要相应更新（v0 纯本地不受影响）。

### 4.5 密钥与后端

- 扩展代码开源，**密钥不能放进扩展**。两条路：
  1. 用户自带密钥（BYOK，存在本地）——适合先自己试；
  2. 小转发后端（如 Cloudflare Worker）保管密钥、按用户限流——正式版。
- 按官方价格，一次判断约几百 token，成本近乎可忽略，可放进免费版；真正的成本是后端本身的运维。

### 4.6 已知技术限制

- Chrome 扩展快捷键（`commands`）只能感知「按下」，感知不到「按住 / 松开」。
  「按住说、松手执行」需要在网页里监听 keydown / keyup，在 chrome:// 等特殊页面无效；
  替代做法是「按一下开始、说完停顿自动结束」，哪里都能用。
- 没选中文字时：按现有关键字兜底（页面标题等），或提示「先选中要搜的文字」。

## 5. 分阶段

| 阶段 | 内容 | 外部依赖 |
|---|---|---|
| **v0** | 快捷键 + 选区旁浮窗 + 现有 offscreen 识别 + 现有别名匹配，关键词 = 选中文字，指令清单由菜单结构生成 | 无 |
| **v1** | 接入 Jev 做路由（BYOK 先自己用 → 转发后端），低置信度给 3 个候选，失败 / 超时（如 > 300 ms）退回本地匹配 | Jev 抢先体验资格；后端 |
| **以后** | 云端语音识别（中英混说更准）、一次说多家（「知乎和 B站都搜」→ 标签组）、按选中内容主动推荐 | 视调研结果 |

## 9. 同次讨论的更大设想（供参考，未定）

这些是 2026-10-18 讨论「随心所欲搜」时的其它方向，语音指令是其中一个入口：

1. **引擎无限多**：接入 bang 语法（DuckDuckGo `!bang` 覆盖一万多个站点；Kagi 也公开过一份列表，授权待确认），中文站点自己补齐；
   用户在任意网站用它的搜索框搜过一次，就提示「要把这个网站加进触触搜吗？」（含 OpenSearch 自动识别）；引擎包一个链接导入。
2. **搜索面板**：快捷键唤出，选中文字自动带入，**拼音首字母**选站（`zh` 知乎、`xhs` 小红书、`bz` B站）；
   地址栏关键字 `cc`（Chrome omnibox 接口）；任何地方认 `量子计算 !zh` 写法。
3. **按内容推荐**：报错 → GitHub / Stack Overflow，商品 → 京东 / 淘宝，书名 → 豆瓣，快递单号 → 快递100，问句 → 速答；
   从个人习惯学习（全部本地）。Jev 的 Choice + 概率也适合做这个。
4. **一次搜多家**：勾选几家一起打开，收进一个标签组，看完一键关。
5. **围墙花园聚合搜索**：用用户自己浏览器的登录态，同时去知乎 / 小红书 / B站 / 微信 / X 搜，抽出前几条结果交给 ChatGPT / Claude / Gemini 总结——
   Perplexity 这类进不去这些站，我们在用户浏览器里天然能做到；现有 X / 知乎提取适配器与 AI 投递链路是地基。适合做付费版核心卖点。

收费相关讨论要点：代码 MIT 开源，本地功能锁不住，能收费的是服务器 / AI 额度 / 持续更新的内容 / 人；
现阶段（129 位用户）瓶颈是用户量，建议先低成本验证付费意愿（赞助、预售页），已免费的功能不收回。
