# 触触搜 v1.6.10 发布说明

发布日期：2026-05-16

## 一句话总览

Service Worker 启动时**预热 prompt / 配置缓存**，把首次冷启动 popup / 侧边栏要做的 6 个 JSON `fetch` 摊到 SW 启动那 50–150ms 窗口里并行做完，等用户实际点开时全是 cache hit —— 直接消灭"首次反应慢"。**无破坏改动、无 storage schema 变化、无新依赖。**

## 主要更新

### 🔧 改进

#### SW 启动时预热 prompt / 配置缓存（消灭"首次反应慢"）

**为什么"只首次卡"？**

之前 `getPopupMenuStructure()` 内部要调 6 个 loader：

- `loadOptimizedPromptConfig` —— prompts/optimizedPrompts.json
- `loadCoverPromptConfig` —— prompts/coverPrompts.json
- `loadTopQuestionsConfig` —— prompts/topQuestionsPrompts.json
- `loadFastAnswersConfig` —— prompts/fastAnswersPrompts.json
- `loadUnifiedMenuConfig` —— config/unifiedMenuConfig.json
- `loadEnginesConfig` —— config/engines.json

每个 loader 内部用 `globalThis.xxxConfig` 做内存级缓存：

```js
if (globalThis.xxxConfig) return globalThis.xxxConfig;  // 二次直接返回
const response = await fetch(url);                       // 首次走 fetch
```

Service Worker 进入空闲后 ~30 秒保留状态，期间所有 loader 直接命中缓存。但只要 SW 彻底卸载（刚安装 / 浏览器重启 / 长时间不动后被回收），下次唤醒就要重新跑全套首次链路：50–150ms 的 fetch waterfall。这就是"为什么只首次卡"。

**v1.6.10 怎么治：**

```
SW 启动那一刻
  │
  ├─ importScripts(...) 加载完所有 JS
  │
  ├─ onInstalled / onStartup / 模块顶层兜底
  │     └─ prewarmPromptConfigs()  ← fire-and-forget
  │           ├─ fetch optimizedPrompts.json  ┐
  │           ├─ fetch coverPrompts.json      │
  │           ├─ fetch topQuestionsPrompts.json│ ─ 并行
  │           ├─ fetch fastAnswersPrompts.json│
  │           ├─ fetch unifiedMenuConfig.json │
  │           └─ fetch engines.json           ┘
  │                       ↓
  │                 缓存全部 hit
  │
  ↓
用户点 popup → getPopupMenuStructure() → 所有 loader if-cache-hit-return → 不再 fetch
```

`_prewarmStarted` 标志位保证幂等，所以三处调用（`onInstalled` / `onStartup` / 模块顶层）哪个先跑都没事，后续调用直接 no-op。

**调用点为什么是这三处？**

| 场景 | 谁触发 | 必要性 |
|---|---|---|
| 首次安装 / 扩展更新 | `onInstalled` | 必备，第一印象就在这一刻 |
| 浏览器启动 | `onStartup` | 必备，每天第一次打开浏览器都过这里 |
| SW 空闲被回收后用户点 popup | **模块顶层兜底** | 上面两个都不会触发，但 SW 因消息事件被唤醒时，init.js 顶层代码必定会跑一遍 |

**用户感知差异：**

| 场景 | v1.6.9 及以前 | v1.6.10 |
|---|---|---|
| 安装后第一次点扩展图标 | 明显"慢一下"（~150–300ms 顿挫） | 流畅打开 |
| 重启浏览器后第一次开侧边栏 | 明显"慢一下" | 流畅打开 |
| 同一会话内反复打开 | 已经很快（缓存命中） | 同样很快（无变化） |

### 🛠 技术改动

- **`background/init.js`**：新增 `prewarmPromptConfigs()` 辅助函数
  - 用 `Promise.allSettled` 容错，单个 loader 失败不影响其它
  - 单 `_prewarmStarted` 标志位幂等，重复调用零成本
  - 在 `onInstalled` 监听器末尾、`onStartup` 监听器末尾、模块顶层兜底三处 fire-and-forget 调用
  - 不阻塞任何主流（包括菜单构建），调试模式下打印一行耗时统计 `[Init] 🔥 prompt 缓存预热完成 (6/6, XXms)`
- **`sidepanel/sidepanel.html`**：暂时隐藏 Stanley / HerName 两个 `<a>` 入口（给 `hidden` 属性）
  - 资料（头像 / 预览图 / 正式 prompts）还没准备好，先不放出
  - 核心代码 100% 保留：`members/` 整个目录（HTML / CSS / JS）、`prompts/stanleyFriends.json` / `prompts/herName.json`、`members.js` 的 GROUPS 注册表、sidepanel CSS / JS 监听、build.sh 的 COPY_DIRS 配置
  - 未来恢复：直接去掉两行的 `hidden` 属性即可
- 改动文件：`background/init.js`（+44 行）、`sidepanel/sidepanel.html`（+2/-1）

## 兼容性

- Chrome 114+（Manifest V3 + `chrome.sidePanel` API）
- 与 v1.6.9 完全兼容；无 storage schema 改动、无新依赖、无破坏 API
- 老用户升级后看到的差异：仅"首次冷启动更快"，其它体验无变化
- 内置封面风格（二次元可爱 / 小红书 / 椰树牌 / 极简留白）功能完全不变
- 侧边栏 Stanley / HerName 入口暂时不可见（资料准备好后下一版恢复）

## 已知限制

- 预热只覆盖 JSON 配置，不覆盖 `importScripts(...)` 的 SW 启动开销本身（这部分要 bundle 工具链才能优化，工程改动更大，暂不动）
- 同一会话内反复开关 popup 本来就不慢（已经缓存命中），所以本次改进只影响"冷启动"那一下
- 浏览器对 SW 唤醒有自己的调度，极端低内存下 SW 卸载更激进，那种场景下 prewarm 的窗口更宝贵

## 升级提示

- 老用户无需任何操作
- 自上次发布只有此 1 个性能改进 + 1 个小调整（隐藏未准备好的入口），**纯增量改动**，零破坏
- 商店上架审核通过后，新装用户直接体验更快的首次冷启动
