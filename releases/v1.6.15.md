# 触触搜 v1.6.15 发布说明

发布日期：2026-05-17

## 一句话总览

Popup 启动数据**全部预热到 `chrome.storage.local`** —— 装/更新完扩展后所有文件就 ready，离线、慢盘、老设备打开 popup 也几乎即时显示。**无破坏改动、无 storage schema 变化、无权限变化、对老用户升级完全静默**。

## 主要更新

### 🔧 改进

#### 1. Popup 首屏 1 次 storage.get 即 render —— 不再做 6 次本地 fetch

**问题背景**：
- v1.6.14 已让 popup 首屏完全脱离 Service Worker（无 sendMessage），但还要做 6 个 `chrome-extension://` **同源 fetch** 拉本地 JSON
- 这些 fetch 不走网络，但在系统繁忙 / 磁盘竞争 / 杀软扫描时仍可能 50-100ms
- 用户反馈"网络不好的时候 popup 还是慢"——其实是系统整体慢拖累磁盘 I/O

**新方案（PUSH-based 预热）**：
- Background 在 `chrome.runtime.onInstalled`（装/更新时）和 SW 冷启动时**预先构建好完整菜单结构**（用 `shared/menuStructureBuilder.js` 同一份纯函数）写入 `chrome.storage.local`
- Popup 一打开先读这个 key（~5ms 量级，比 6 次本地 fetch 快几倍）
- 命中 → 直接 render；未命中（首装首次秒点 / version 不匹配 / storage 异常）→ 自动 fallback 到 v1.6.14 的 fetch 路径

**与 v1.6.13 旧 cache 的本质区别**：
- v1.6.13：**popup 自己写 cache**（render 后才写），存在"双源"——fresh 回来时会 re-render → 视觉抖动
- v1.6.15：**只有 background 写 cache**（单向 push），popup 只读。单源、无抖动、永远 fresh

#### 2. 侧边栏按钮 label 即时显示

**问题背景**：
- 打开 popup 时，底部"📑 打开侧边栏 / 📕 关闭侧边栏"按钮文字需要等 `sendMessage` 给 SW 拿状态才能确定
- SW 冷启动 + 消息往返：50-300ms
- 用户可能看到按钮文字"短暂闪烁/切换"

**新方案**：
- SW 在 sidepanel 的 port 连接/断开时主动把状态写到 `chrome.storage.local['ccs_sp_open_<windowId>']`
- Popup 启动时优先读 storage（即时显示 label），同时异步向 SW 校验
- 在罕见的不一致场景（storage 陈旧），SW 回来的权威值会更新 label

## 兼容性

- Chrome 114+（Manifest V3 + `chrome.sidePanel` API）
- 与 v1.6.14 完全兼容；**无 storage schema 改动、无权限改动、无新依赖、无破坏 API**
- 对老用户升级**完全静默**（无权限弹窗、不被停用）
- 新增 storage key：`ccs_popup_menu_prewarm`（~10KB）/ `ccs_sp_open_<windowId>`（< 100B 每个窗口）。远低于 10MB 配额，无风险

## 期望效果

| 指标 | v1.6.14 | v1.6.15 目标 |
|---|---|---|
| Popup 首屏 TTFB（SW warm） | ~50-100ms | **< 30ms**（storage hit） |
| Popup 首屏 TTFB（SW 冷） | ~100-200ms | **< 50ms**（storage hit）/ ~100ms（fallback） |
| 首装第一次点 icon | ~150-250ms | ~50ms（onInstalled 完后）/ ~200ms（onInstalled 未完，fallback） |
| 网络/磁盘慢时 popup 响应 | 用户感觉慢 | **几乎无感**（1 次 storage.get 不依赖磁盘 fetch） |
| 侧边栏按钮 label 出现 | ~50-300ms 等 SW | **< 5ms**（先读 storage） |
| 首屏 fetch 次数 | 6 | **0**（命中时）/ 6（fallback） |
| 首屏 sendMessage 次数 | 0 | **0** |

打开 popup devtools console 可看 `[触触搜][PERF] popup TTFB: XXXms (storage-prewarm)` 或 `(local-fetch)`，区分走了哪条路径。

## 已知限制

- **首装且立即点 icon**：用户装完扩展后 onInstalled 是异步事件，可能还没写完 storage 就被用户秒点。此时走 fallback 路径，体验等同 v1.6.14（~150ms 首屏）。从第二次打开起 100% storage 命中。
- **执行菜单仍依赖 SW**：用户点了菜单后 `executeMenuAction` 还要 sendMessage 给 SW。SW 冷时这一步仍可能延迟 200-400ms 才打开标签。这是已知遗留，本次未解决（同 v1.6.14 注记，要复刻 TextLimits / keyword resolver 整套到 popup 才能解决）。**重点**：首屏可见时间不受影响。
- 本版本只动了 popup 启动数据预热相关代码。侧边栏 / 右键菜单 / 内容脚本行为与 v1.6.14 一致。

## 升级提示

- 老用户**无需任何操作**，自动更新静默升级
- 自上次发布共 1 个 commit（涉及 3 个 JS 文件 + 4 个发版 meta）
- 商店上架本次为内部性能优化，**不触发权限审核**，审核通常 < 24h 通过
- 升级后 onInstalled 触发即写 cache，第二次打开 popup 即可享受新速度

## 回滚预案

如新版本出现严重问题：

```bash
git revert <commit-hash>           # 一行回滚
# 或急救
git reset --hard pre-popup-prewarm
```

`pre-popup-prewarm` tag 已打在本次重构前。即使 cache 路径全坏，v1.6.14 fetch fallback 自动兜底，最坏体验 ≈ v1.6.14。
