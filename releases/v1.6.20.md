## 一句话总览

## 主要更新

### 🐛 修复

#### 1. 扩展 reload 后事件监听器叠加（CRITICAL）

**症状**：开发者在 `chrome://extensions/` 反复点 reload，或某些场景下扩展自动 reload，每次都会让所有 content scripts 重新跑一遍。结果：page 上累积越来越多重复的事件监听器，最终可能导致选区监听卡顿、右键菜单触发多次、悬浮面板重叠等。

**根因**：manifest 配置 `content_scripts.run_at=document_start + all_frames=true`，每次扩展生命周期事件都触发新一轮注入。content.js + dockbar.js + 20 个 modules 顶层都是 IIFE 直接 `addEventListener` 风格，共 44 个事件监听器全部匿名 arrow 函数无法 `removeEventListener`。原代码只有 `window.CCSModules ||= {}` 弱命名空间守卫，不阻断 IIFE 顶层执行。

**修法**：`content.js` + `dockbar.js` 顶部加幂等守卫：

```js
const __g = typeof globalThis !== 'undefined' ? globalThis : window;
if (__g.__ccs_content_initialized) return;  // (dockbar 用 __ccs_dockbar_initialized)
__g.__ccs_content_initialized = true;
```

第二次注入直接 return，避免顶层副作用重跑。首次注入路径完全不变。

#### 2. dockbar 底栏关闭后仍空转 2 秒心跳（CRITICAL）

**症状**：用户在悬浮面板设置里点 undock / close 关闭底栏后，DevTools console 里仍能看到每 2 秒触发一次 `[DockBar]` 相关检查，CPU 永不空闲（虽然 if 短路成 no-op，但事件循环 wake-up 无法避免）。

**根因**：`dockbar.js:369` 启动 `setInterval(..., 2000)` 但**返回值没存到任何变量** —— 没有 `clearInterval` 的可能。即使设置 `globalDock=false` 或 `barClosed=true`，poller 仍每 2 秒醒来检查一次。

**修法**：
- 把 setInterval 返回值存到 `this._visibilityTimer`，并加重复创建守卫
- 新增 `stopVisibilityTimer()` / `destroy()` 两个清理方法
- `undock()` / `close()` 触发时调用 `stopVisibilityTimer()`

**未处理**：`settingsPanel.js` 的 globalDock checkbox 没接 callback 到 content.js → DockBar，那条路径仍是"timer 跑但 no-op"。这是 pre-existing plumbing 缺口，不在本轮范围。

#### 3. SPA 监控 observer 泄漏 + history wrap 嵌套（CRITICAL）

**症状**：扩展 reload 一次后，再去 BiliBili / Twitter / GitHub 这种 SPA 站点切换路由，关键字更新可能延迟、卡顿、或触发多次。

**根因**：`modules/realtimeUpdate.js` 三处问题：

1. `titleObserver = new MutationObserver(...)` 存在局部 const 里，`stopMonitoring()` 不调 disconnect → orphan observer
2. `popstate` listener 用匿名箭头函数，无法 `removeEventListener`
3. monkey-patch `history.pushState / replaceState` **没存原函数引用、没"已包装"标记** → 第二次 startMonitoring 把已包装版本再包一层，路由切换时调用栈嵌套

**修法**：
- `startMonitoring()` 顶部加 `_monitoring` 幂等守卫
- `titleObserver` / popstate listener / 原函数全存到 `this._titleObserver / _onPopState / _origPushState / _origReplaceState`
- 包装函数加 `wrapped.__ccs_wrapped = true` 标记，包装前先检查
- `stopMonitoring()` 完整还原：disconnect observer、removeEventListener popstate、还原 history.pushState（且只在确认是本模块包过的情况下，避免覆盖其它扩展的包装）

#### 4. 黑名单管理理论 XSS 隐患（MED）

**症状**：用户打开 popup → 设置 → 黑名单管理。理论上，如果有恶意 co-installed 扩展通过 `chrome.storage.local.set` 把 `<img src=x onerror=alert(1)>` 塞进 `ccs_settings.blacklist` 数组，popup 渲染时会执行该脚本。

**根因**：`popup/popup.js:914` 和 `popup/modules/SettingsManager.js:236` 两处用模板字面量把 host 直接拼到 `innerHTML`，包括 `data-host="${host}"` 属性。host 来自 chrome.storage，未做转义。

**修法**：复用既有 `PromptLibraryManager._escapeHtml` 的 `textContent → innerHTML` 模式，加私有方法 `_escapeHtml(text)`，两处 map 渲染前过它，data-host 属性也走转义（`"` 会破属性结构）。

**验证 SOP**：DevTools console 执行
```js
chrome.storage.local.set({ccs_settings:{blacklist:['<img src=x onerror=alert(1)>']}})
```
然后开 popup → 设置 → 黑名单管理 → 不弹 alert，host 文本以原样字符串呈现。

#### 5. sidepanel onMessage handler 签名缺残（MED）

**症状**：当前不会立刻崩，但 handler 内任意分支抛错会牵连整条消息监听 stack，影响 sidepanel 其它正常路径。

**根因**：`sidepanel/sidepanel.js:1291` 的 `chrome.runtime.onMessage.addListener((message) => ...)` 签名缺 sender 和 sendResponse 参数，且 handler 内部无顶层 try/catch。

**修法**：
- 签名补全 `(message, sender, sendResponse) =>`
- 加 `typeof message !== 'object'` 兜底
- 所有 known action 分支显式 `return false`（同步处理无需异步响应）
- 加顶层 try/catch + warn 日志兜底

**未做**：sender.id 来源校验。sidepanel 接收的都是 background 内部 push，不存在跨扩展通信场景，加 origin 校验目前没收益，后续真需要时再补。

### 🔧 改进

#### 拖动悬浮面板更顺滑（MED）

**症状**：拖动触触搜悬浮面板时，鼠标移动可能感觉粘滞或丢帧，特别是页面较复杂时。DevTools Performance 录制能看到 mousemove 处理时间不稳定，偶有 long task。

**根因**：`modules/dragging.js:39` 之前直接 `document.addEventListener('mousemove', e => handleDragging(e))`。一次正常拖拽（鼠标走 50-300 像素）= 50-300 次回调，每次都走完整 `getBoundingClientRect` + 边界计算 + style.left/top 写入。这是 Layout thrashing 的典型形态。

**修法**：用 `requestAnimationFrame` 合并 —— 多个 mousemove 在一帧内只跑一次 handleDragging，用最新事件位置。视觉与高频更新等价（60fps 是人眼极限），但主线程从 100-300 calls/拖拽 降到 ≤ 60 calls/拖拽。

```js
let pendingFrame = null;
let lastEvent = null;
const onMouseMove = (e) => {
  lastEvent = e;
  if (pendingFrame != null) return;
  pendingFrame = requestAnimationFrame(() => {
    pendingFrame = null;
    const evt = lastEvent;
    lastEvent = null;
    if (evt) this.handleDragging(evt);
  });
};
```

## 已知限制

- 设置面板里通过 checkbox 关闭 globalDock 的路径不经过 `DockBar.undock()`，那条路径下 visibility timer 仍是"跑但短路 no-op"状态。需要后续在 settingsPanel callback 链里补一节才能彻底关掉，本轮先放着。
- 本轮不动 `chrome.runtime/tabs.sendMessage` 的全量路由迁移（66% 调用点旁路 `shared/runtimeClient.js` wrapper）—— 改动面 26+ 文件、风险中等，留下一轮。同理 storage 封装迁移也延后。

## 升级提示

从 v1.6.19 升级：商店推送后浏览器自动更新即可。**无用户可见行为差异**（除了拖动更顺滑、blacklist 管理更安全）。技术债清理 + 长生命周期资源泄漏修复占大头。

如果你是开发者反复 reload 扩展做调试，这次升级最大收益是：**reload 100 次后页面里的事件监听器仍是 44 个，而不是 4400 个**。
