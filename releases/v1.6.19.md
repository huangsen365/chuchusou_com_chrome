# 触触搜 v1.6.19 发布说明

发布日期：2026-05-17

## 一句话总览

**修复 v1.6.18 zip 装上后 Service Worker 直接起不来（Status 15）+ popup/sidepanel 在 Chrome Web Store 安装后首次打开卡顿 5-10 秒**。两个独立 bug 一并修。manifest 的 SW 入口切到 Plasmo TS bundle `static/background/index.js`，popup/sidepanel 启动彻底脱离 Service Worker。

## 主要更新

### 🐛 修复

#### 1. v1.6.18 zip 装上 Service Worker 注册失败（Status 15）

**症状**：安装 v1.6.18 zip 后扩展卡片显示红色错误"Service worker registration failed. Status code: 15"，扩展所有功能（右键菜单、popup、sidepanel）全失效。

**根因**：build pipeline (`scripts/plasmo-compat-postbuild.mjs`) 把 manifest 的 `service_worker` 入口强制回退到 legacy `background/index.js`，注释里写"未经 Chrome 真机回归"出于谨慎。但 v1.6.18 内部 6 个 commits (`9437c35..725b45d`) 已经把 `base.js / Logger.js / menuBuilder.js / menuHandlers.js / voiceOffscreenBridge.js / init.js` 从 legacy `index.js` 的 `importScripts` 列表里 drop 掉了（迁到 TS port）。结果：

- legacy SW 加载时，`events.js` 顶层第一行 `chrome.runtime.onInstalled.addListener(createContextMenus)` 拿到的 `createContextMenus` 是 `undefined`（menuBuilder.js 不再 importScripts）
- 顶层 ReferenceError → Service Worker 注册失败 → 整个扩展起不来

**修法**：postbuild 强制把 manifest SW 入口写为 `static/background/index.js`（Plasmo TS bundle），由它正确接入所有 TS port 模块。其它 3 个 popup/sidepanel/content_scripts 入口保持 legacy，等各自 TS port 1:1 后再单独切。

**漏检原因**：`verify-plasmo-compat-build.mjs` 只校验文件存在 + JS 语法，没模拟 SW 加载，所以连续 6 个 drop legacy 的 commit 都没拦下来。后续计划加一个 vm sandbox SW smoke test。

#### 2. TS attach* 加载时序 bug（v1.6.18 zip 同时存在但被 bug #1 掩盖）

**症状**：修完 bug #1 把 SW 入口切到 Plasmo bundle 后，发现还是 Status 15。

**根因**：`src/background.ts` 之前的顺序是

```ts
import { attachBaseBridge, attachMenuBuilder, attachMenuHandlers, autoRegisterVoiceBridge, attachInit } from "..."
sw.importScripts(/* 18 个 legacy */)
attachBaseBridge()
attachMenuBuilder()
attachMenuHandlers()
autoRegisterVoiceBridge()
attachInit()
```

历史架构假设是"legacy 提供 X，TS attach* 在后面 override X"。但 6 个 drop commits 之后 legacy 不再提供 `createContextMenus / setMenuState / logMenuEvent` 等全局函数。`importScripts` 加载 `events.js` 时，它顶层第一行 `addListener(createContextMenus)` 在 attachMenuBuilder() 之前执行 → globalThis 上还没这个函数。

**修法**：把 4 个 lazy attach 前置到 `importScripts` 之前

```ts
attachBaseBridge()      // 注入 setMenuState / applyMenuTitle / logMenuEvent
attachMenuBuilder()     // 注入 createContextMenus / COVER_PIN_MENU_ID
attachMenuHandlers()    // 注册 chrome.contextMenus.onClicked
autoRegisterVoiceBridge() // 注册 voice offscreen 监听器
sw.importScripts(...)   // legacy events.js 顶层引用 globalThis.X 已就位
attachInit()            // 依赖 g.MenuSystem / initKeywordSyncSystem 已 importScripts 就位
```

`attachInit()` 保留在最后 —— 它在 attach 时直接读 `g.MenuSystem`、`g.initKeywordSyncSystem`（来自 `menuSystem.js` / `keywords.js`），必须在 `importScripts` 完成后调用。

**验证**：写了一个 vm sandbox 模拟（stub `chrome.*` + `importScripts`），SW bundle 顶层评估成功，18 个 importScripts 全部加载，`createContextMenus / setMenuState / logMenuEvent / MenuSystem` 在 bootstrap 后全部就位。

#### 3. popup / sidepanel 在 Chrome Web Store 安装后首次打开卡顿 5-10s

**症状**：用户报告

1. 商店更新触触搜 → 打开新标签页（baidu.com）→ 点 popup 图标 → 卡很久
2. 等很久才渲染
3. 新标签 → 新网站 → 点 popup → 又卡
4. 切回原标签 → popup 秒开
5. 新页面再来一次 → 卡，popup 干脆打不开

**根因**：popup/sidepanel 启动时给 background Service Worker 发 `sendMessage(getKeyword)` 同步等回包。Chrome MV3 Service Worker 有 30s idle eviction，新标签页/新网站会触发 SW 冷启动 —— 启动需要 importScripts 17 个 legacy 文件（~270KB），主线程 CPU 满载 200-500ms，popup 进程被抢占等不到回包，所以卡。原标签页 popup 秒开是因为之前打开过 popup → SW 已经热，sendMessage 立即回。

**修法**：popup / sidepanel 启动彻底脱离 SW：

- **关键字**：popup/sidepanel 启动时读 `chrome.storage.local`（不依赖 SW），并装 `chrome.storage.onChanged` 监听器跟着 background 写入实时刷新。fallback 走 `sendMessage(getKeyword)` 1500ms 超时降级。
- **菜单结构**：build 时跑 `scripts/prebuild-popup-menu.mjs`，用 `CCSMenuStructureBuilder` 把 23 个 popup 菜单项 / 19 个 sidepanel 菜单项编译成静态 HTML 直接注入 `build/popup.html` / `build/sidepanel.html`。container 上挂 `data-static-built="true"`，前端 JS 检测后跳过 `render()`。**首装首次打开也不依赖 storage / fetch / SW** 就能看到菜单。
- **次要请求推迟**：`setupSidePanelButton` 的 `getSidePanelState` 消息和 sidepanel `setupAlivePort` 都包到 `requestIdleCallback`，不和首屏争 CPU。
- **sidepanel alive port**：sidepanel 打开时建一条 `chrome.runtime.connect('sidepanel-alive')` 长连接，SW 在 sidepanel 开着的全程不会被 idle evict。

**效果**：popup 启动从「卡 5-10s 等 SW 冷启动」变成「即开即用」。本地 perf 测试 popup 首帧 < 50ms（含 Plasmo bundle 191KB 解析）。

### 🛠 技术改动

#### popup / sidepanel 渲染机制 10 步精简

popup.js 1380 → 1077 行（-303 行），sidepanel.js 1751 → 1682 行（-69 行），净减 -367 行。逐步删除：

- Step 1：剔除首屏 `sendMessage(getKeyword)`（用 storage cache）
- Step 2：删除 storage prewarm 路径（-109 行）
- Step 3：build 时预生成菜单结构 JSON（6 fetch → 1 fetch）
- Step 4：`render()` 用 DocumentFragment 原子 swap，静态骨架不闪空白
- Step 5：`setupSidePanelButton` 校正消息推迟到 idle
- Step 6-8：cover 配置内联 + script defer + 生产诊断 trace
- Sidepanel：同款解耦 SW 改造（getMenuStructure / getKeyword / alivePort）
- Step 9：菜单全静态 HTML 注入 —— 生产 0 JS DOM 构建
- Step 10：删除冗余机制层（render / fetch / prebuilt JSON 层全删）—— 净删 -367 行

popup bundle 191KB / sidepanel bundle 174KB，perf-budget 都在预算内。

#### 6 个 background legacy 模块 drop 到 TS port

`base.js (889) / Logger.js (458) / menuBuilder.js (990) / menuHandlers.js (611) / voiceOffscreenBridge.js (100) / init.js (448)` —— 共 2506 行 legacy 由 `src/background/*.ts` 取代。剩余 17 个 legacy 通过 importScripts 加载。SW bundle 77KB（perf-budget 150KB 限内）。

剩余 2 个 listener 主体仍在 legacy：`background/{events.js, menuBuilder.js}` 包含 `chrome.tabs.onUpdated / chrome.runtime.onConnect / chrome.runtime.onMessage / chrome.contextMenus.onShown` 等 listener 注册，需要 Chrome 真机回归 ≥ 20 路径之后再 port。

## 兼容性

- Chrome 114+（不变）
- Manifest V3
- 关键依赖：`chrome.storage.local`、`chrome.runtime.connect`、`requestIdleCallback`（fallback `setTimeout`）

## 已知限制

- 首次安装 / 重装时 popup 菜单内的"动态部分"（百问子菜单的 100 个候选题）依然需要 SW 来回，因为这部分量大不适合静态注入；这些菜单项目首次打开有 < 1s 的填充延迟，之后 storage cache 命中即开即用。
- popup 启动后台 fetch 的 `coverPrompts.json` 仍走老路径，首次需要 ~50ms 网络/磁盘 IO，但不阻塞菜单显示。

## 升级提示

从 v1.6.18 升级：商店推送后浏览器自动更新即可。**v1.6.18 zip 装不上的 Status 15 错误在 v1.6.19 完全消失**。如果你之前装过 v1.6.18 zip 但卡在 Status 15，建议：

1. `chrome://extensions/` → 触触搜 → 移除（不是 reload —— manifest 入口变了）
2. 装 v1.6.19 zip
3. 重启 Chrome（清理 SW 冷启动残留）
4. 验证：右键菜单、popup、sidepanel 三个入口选中文字 → 关键字正常显示

从 v1.6.17 或更早升级：路径相同，效果相同 —— popup / sidepanel 装上首次打开应该秒开，不再卡 5-10s。
